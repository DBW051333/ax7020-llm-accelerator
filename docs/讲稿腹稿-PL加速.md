# 展示腹稿：用 PL 加速大模型推理（AX7020 + Qwen2.5-0.5B）

> 时长按 12~15 分钟设计；【】里是配合展示的动作/画面；所有数字均为板端实测或标注的推算。

## 开场（0.5 分钟）

一句话定位：

> 我们在 ALINX AX7020（Zynq-7020）上部署了 Qwen2.5-0.5B-Instruct，并把 Transformer 中算术最密集的部分搬进 PL，用四路 DMA 流水线做矩阵加速。实测文本生成速度从 0.541 提升到 0.747 token/s，提升 37.5%；同时给出了资源预算和理论上限的完整分析。

## 第一部分：为什么 LLM 适合用 PL 加速（2 分钟）

**1. decode 的本质是"流式矩阵-向量乘"。**
大模型每生成一个 token，就是把整个网络前向一遍：24 层 Transformer，每层是几次大矩阵乘（Attention 的 Q/K/V/O、FFN 的 Gate/Up/Down），最后过一次 LM Head。对我们这个模型，每个 token 合计约 **4.94 亿次乘加**。这不是 batch 计算，是严格的串行数据流——所以关键不是"算得多快"，而是"数据能不能不断流进计算单元"。

**2. 瓶颈在搬运，量化让搬运变轻。**
模型权重用 GGUF 量化格式存储：Q4_K 每权重 4.5 bit、Q5_0 约 4.7 bit、Q8_0 8.5 bit，每 32 个权重共享一个 FP16 缩放系数。这对硬件极其友好——解码只需要拆 nibble 和移位，乘加是整数运算，浮点只集中在少量缩放系数上。一个 0.5B 模型压到 374MB，Zynq 的 DDR3 和 PL 的流式接口才喂得动。

**3. 我们的设计原则：流式，而不是驻留。**
权重不可能放进 BRAM（全模型 374MB vs BRAM 总共 630KB），所以架构是"DMA 流式喂料、计算阵列按线速消化"——每一拍都有新权重进来、有乘加在做。PL 的价值在这里：定制一条从 DDR 到乘加阵列的直通数据通路，4 个 HP 口并行，每口 64-bit。

## 第二部分：系统怎么工作（3 分钟）

**1. 分工（对照数据流图）。**
PS 上的 ARM 双核跑 llama.cpp（固定上游版本 + 自研集成补丁）：嵌入查表、Attention 的 softmax、RMSNorm、激活量化、采样都在 CPU；PL 做矩阵乘。当前板载配置：**每层 FFN 的 Gate/Up 两个 [4864×896] 的 Q5_0 矩阵乘、SiLU 激活和逐元素乘法**由 PL 四路并行完成，一次调用返回 4864 个结果。

【动作：切到数据流图（decode 五阶段流程图）】

**2. 数据通路。**
CPU 把 896 维激活量化成 Q8_0（28 个块），和权重包一起经 4 个 AXI DMA、4 个 HP 口送进 PL——每个 lane 分到 1216 行。lane 内部：激活装进 BRAM 供 Gate/Up 两组权重复用；Q5_0 数据流按"每超块 18 拍"协议进来，整数点积阵列每拍吃 8 个权重×8 个激活。

**3. 算术设计（重点讲三条）。**
- **整数点积 + FP16 尺度**：每个 32 元素块内是纯整数乘加（精确、无舍入），块间用 FP16 缩放系数做精确的定点累加，整行只做一次 FP32 舍入。这让硬件结果和 CPU 参考的对齐有明确的数值契约（逐层 relative L2 ≤ 1e-4 校验）。
- **SiLU 硬融合**：sigmoid 用 8192 项 Q30 ROM 查表 + 线性插值，Gate/Up 两个点积的结果不出芯片直接做 SiLU(g)·u——省掉一次 4864 维向量的 DDR 往返。
- **工程细节举一个例子**：我们用"权重乒乓缓冲"让 DMA 流领先计算两个块，"至多一个在途结果"的反压链保证流/计算/回传三段永不乱序，"权重字预算"防止跨包错位——这三个机制是吞吐从每子块 15 拍压到 4 拍的关键。

**4. 资源账（当前 v5 配置）。**
LUT 44%、DSP 仅 11%（点积是 LUT 整数算术，DSP 只做几个 FP 乘法）、BRAM 60%（激活缓冲 + sigmoid ROM）。83.33MHz 下时序收敛 WNS +0.42ns。

## 第三部分：实测结果（2 分钟）

【动作：切到实测结果表；或现场跑一次聊天演示】

| 路径 | 24-token decode | 速度 |
| --- | ---: | ---: |
| 纯 CPU | 42.3 s | 0.541 tok/s |
| **PL 融合加速** | **30.8 s** | **0.747 tok/s（+37.5%）** |

- 每层一次融合调用，一次生成 24 token 共 **553 次硬件调用**，全部通过与同输入 CPU 参考的数值校验（最差相对误差 9.8e-7，远小于 1e-4 契约）。
- 加速来源分解：DMA 窗口 + 后端计算合计从每步 621ms 压到 483ms，其余收益来自 SiLU 融合省掉的往返。
- 现场演示：`bash run.sh` 打字聊天——预期每个 token 约 1.3 秒，语速和人打字相当；退出时打印的 STATS 行就是本次运行的硬件调用凭证。

**诚实声明（主动讲）**：PL 生成文本与纯 CPU 不完全相同——量化近似算术的微小误差会被 24 层网络放大，我们已经把首个分歧定位到具体算术环节；"提速"与"输出逐字一致"是两个独立的验收目标，当前前者达标、后者未解决，质量等价性（困惑度/任务指标）是下一步工作。

## 第四部分：瓶颈分析与路线图（3 分钟）——这部分展示深度

**1. 把每步 1.35 秒拆开**：PL 派发占 483ms，CPU 还剩 866ms——Down 投影约 341ms、Attention 约 259ms、LM Head 约 444ms。也就是说，当前只搬走了 Gate/Up，大头还在 CPU。

**2. 迁移路线（按收益/难度排序）**：Down 入 PL（Q4_K 引擎已验证，Q6_K 加解码）→ Attention 入 PL（与 Gate/Up 同为 Q5_0，卡点是协议）→ LM Head（算力够，但受带宽封顶）。

**3. DSP 的角色**：板上 196 片空闲 DSP48E1 可以做每片每拍 2 次的位精确 int8 乘加（16 位车道隔离），用 32~64 片就能把 Q4_K/Q6_K 引擎的整数 MAC 从 LUT 搬进 DSP——让"一套 overlay 同时装下 Gate/Up + Down 两套引擎"成为可能（粗叠加 55k LUT 超出器件，DSP 化后 66% 装下）；且同层内 Gate/Up 与 Down 串行执行，MAC 阵列可分时复用。

**4. 理论上限**：每 token 必须从 DDR 读约 392MB 权重（decode 无权重复用），实测 4 个 HP 口聚合带宽 1.96GB/s → **单流上限约 5.0 token/s**。当前 0.747 距上限 6.6 倍，可见路线（0.9 → 1.0 → 2.5~4）都碰不到墙；突破 5 tps 只能靠提频、降精度或批量共享权重。

## 结尾（0.5 分钟）

> 总结三句话：第一，我们把 Qwen 的 FFN Gate/Up 用四路流式引擎搬进了 PL，数值有契约、性能 +37.5%；第二，我们给出了从资源、协议到带宽上限的完整量化分析——单流 5 tps 是这套硬件的天花板，且给出了到达路径；第三，我们明确标注了未解决的问题：生成文本与 CPU 的一致性和质量等价评估。下一步是 Down 与 Attention 的迁移，预期把速度再提一倍以上。

## 附：预答问题（Q&A 弹药）

| 可能的提问 | 要点 |
| --- | --- |
| 为什么只有 +37.5%，不多做点？ | Down/Attention/LM Head 仍在 CPU；迁移路线已验证到第 2 步，预期 0.9→4 tps；本演示聚焦已验收的部分 |
| 为什么点积不用 DSP？ | 当前 LUT 版本时序收敛、资源够；196 片空闲 DSP 规划为 Q4_K/Q6_K 引擎的 MAC（2 MAC/片/拍位精确打包），是下一阶段统一 overlay 的前提 |
| 硬件结果怎么保证正确？ | 三层：仿真位级对拍（新旧引擎 68 行逐位一致）、逐层 relative L2 ≤ 1e-4 板级校验（553/553）、五模式重复性测试（输出逐字节一致） |
| 为什么生成文本和 CPU 不一样？ | 量化近似的微小算术差异（1e-6 量级）被 24 层网络放大到改变采样排序；已定位到具体环节（整数 MAC 后的系数路径）；修复需要改变数值契约或更接近 CPU 的舍入，属后续工作 |
| 5 tps 上限怎么算的？ | 392MB/token（每权重每 token 必读一遍）÷ 1.96GB/s（4×HP 口实测聚合带宽，667 理论值的 74%）；compute 侧 4.94 亿 MAC/token 对 DSP 阵列只需 ~30ms，不是瓶颈 |
| 速度对用户体验如何？ | 0.75 token/s ≈ 每秒 1.5 个汉字，接近人阅读速度；LM Head 迁移后预期 2.5~4 tps 即明显流畅 |
